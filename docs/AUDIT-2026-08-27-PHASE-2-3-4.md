## Phase 2 — Documentation vs reality

### [CRITICAL] Safety docs describe webhook authentication that is switched off on a publicly-reachable API

**Location**
- `app/backend/.env:17-18`
- `app/backend/app/api/routes/webhooks.py` (auth guard)
- `app/backend/app/core/config.py` (`webhook_auth_enabled`)
- `app/docs/safety.md`, `app/docs/backend-execution.md`
- live ngrok tunnel: `https://paxton-transocular-christinia.ngrok-free.dev -> http://localhost:8000`

**Evidence**
`.env` contains both:

```
WEBHOOK_AUTH_SECRET=toa_long_secret_string
WEBHOOK_AUTH_ENABLED=false
```

`ss -lntp` shows the trading API on `127.0.0.1:8000`, and the ngrok agent (pid 2328) forwards a
public HTTPS URL to exactly that port. `tests/test_webhook_authentication.py::test_webhook_unauthenticated_request_rejected`
currently fails with `202` instead of `401` because `get_settings()` reads the real `.env`.

**Problem**
`POST /api/webhooks/tradingview` accepts unauthenticated order injection from the public
internet. Because the tunnel points at the trading API itself (not at `demo_streaming`), *every*
`/api/v1/*` route is public too: account/allocation mutation, broker flatten, reconcile.

Note the path: `main.py:192` mounts the webhooks router at `prefix="/api"` while `main.py:193`
mounts everything else at `/api/v1`. The webhook is the only route outside `/api/v1`, which is why
several docs cite it as `/api/v1/webhooks/tradingview` — a path that 404s.

**Fix**
Set `WEBHOOK_AUTH_ENABLED=true`, invert the default in `config.py` so absence means enabled, and
restrict the tunnel to the webhook path only.

**Confidence** high — verified live on the host.

### [HIGH] `.env.example` cannot produce a working system, and omits every security setting

**Location** `app/backend/.env.example`; `app/backend/app/core/config.py:31-32`; `app/backend/alembic.ini:89-90`

Walking a clean machine through `cp .env.example .env` step by step:

1. `DATABASE_URL` is **absent from `.env.example` entirely**. The code falls back to the hardcoded
   default at `config.py:31-32`, `postgresql+asyncpg://root:root123@localhost:5433/ibkr_trading`.
   This happens to work only because that default matches the live container. On any machine
   without a Postgres on port 5433 with user `root`, startup fails at the first session checkout,
   with no hint in the example file that a DSN was ever needed.
2. `ALLOCATIONS_CONFIG_PATH=config/paper_allocations.yaml` points at a file that does not exist
   anywhere in the repo (Phase 1 F-06). Nothing reads it, so it fails silently rather than loudly —
   which is worse, because the operator believes allocations came from YAML when they came from the
   `allocations` table.
3. `IBKR_PORT=7497` (TWS). The live deployment runs IB Gateway on `4002`. Following the example
   connects to nothing. `tests/test_tws_connection.py::test_default_configuration` asserts `7497`
   and currently fails with `4002`.
4. `WEBHOOK_AUTH_SECRET`, `WEBHOOK_AUTH_ENABLED`, `EMERGENCY_KILLSWITCH_AUTH_SECRET` and
   `EMERGENCY_KILLSWITCH_AUTH_ENABLED` appear nowhere. A clean install is unauthenticated by
   construction and has no armed kill switch.
5. `TRADING_SYMBOL`, `CANDLE_TIMEFRAME`, `STRATEGY_CANDLE_COUNT`, `ORDER_QUANTITY` are leftovers
   from the single-symbol candle strategy. `Settings` still defines them but no execution path
   reads them.

**Problem** Every one of these is silent. `extra="ignore"` on the settings model means a typo or an
obsolete key is discarded without a warning, so none of the five surfaces at startup.

**Fix** Regenerate `.env.example` from the `Settings` field list, mark required-vs-optional, and
switch `extra` to `forbid` (or log unknown keys) so drift becomes visible.

**Confidence** high.

### [MEDIUM] The critical-recovery retry machinery is dead code

**Location** `app/backend/app/services/critical_recovery.py:99-106, 169-176, 232-239, 255-262, 286-293`

## Phase 4 — Is it actually connected?

### [CRITICAL] A shared dict mutated by the broker callback while the persister iterates it aborts order persistence *after* the orders are live at IBKR

This is the most serious finding in the audit, and it has already happened twice today in production.

**Location**
- `app/backend/app/oms/coordinator.py:996` — `for execution in order.executions.values():`
- `app/backend/app/oms/ibkr_adapter.py:670` — `order.executions[exec_id] = record`
- `app/backend/app/oms/coordinator.py:983-1001` — `_persist_child`
- `app/backend/app/services/order_manager.py:508` — `outcomes = list(await asyncio.gather(*tasks))`
- `storage/logs/2026-08-27/trading.log:33370-33401`, `:42544`

**Evidence** `_persist_child` iterates `order.executions.values()` and `await`s
`exec_repo.upsert(...)` inside the loop. Every `await` yields the event loop, and the adapter's
`execDetails` handler inserts new execution records into that same dict. The result, from the log:

```
File ".../app/oms/coordinator.py", line 912, in _persist_child
  for execution in order.executions.values():
RuntimeError: dictionary changed size during iteration
```

The exception propagates up `_persist_child` → `coordinator.execute` (line 202) →
`_evaluate_and_submit_locked` → `_fanout_single_account` → `asyncio.gather` → the worker, which
marks the job `FAILED`. Crucially the very next log lines are:

```
CLOSE_ORDER_SUBMITTED: internal_order_id=ORD-320-...-CLOSE-L0 broker_order_id=2748 symbol=KIE
OMS submit_one_leg handoff: ... leg=2/2 symbol=XLP side=BUY qty=273.0 order_type=MARKET
```

The orders are at the broker. The persist is what failed.

**Problem — three separate failures, all silent:**

1. *The system reports the opposite of what happened.* Job `e9d9148c-c6c2-4d8d-9eb7-69e3c50579a4`
   is `FAILED` with `last_error = 'dictionary changed size during iteration'`, and the log records
   `status=REJECTED db_pk=308`. Meanwhile the `orders` table holds 26 `:CLOSE-*` rows for that trade
   with broker ids 2742–2767, all `FILLED`. A rejected close that filled.

2. *Two accounts are left with one leg of a pair.* For trade
   `MBG-AMEX:KIE-AMEX:XLP-20260827T1100`, twelve accounts have both `:CLOSE-L0` and `:CLOSE-L1`.
   Accounts **294** and **297** have only `:CLOSE-L0`:

   | account | OPEN L0 | OPEN L1 | CLOSE L0 | CLOSE L1 |
   |---|---|---|---|---|
   | 294 | 393 KIE | 273 XLP | 336 (partial) | **missing** |
   | 297 | 629 KIE | 436 XLP | 629 | **missing** |

   The hedge is gone and the residual XLP leg is naked directional exposure. Account 294 additionally
   closed only 336 of 393 KIE.

3. *The two sides of the state disagree.* `signals.id=308` reads `status = PROCESSED` while its job
   reads `FAILED`. Reconciliation, the dashboard, and the RMS position view will each pick a
   different answer.

**Fix** Snapshot the dict (`list(order.executions.items())`) before the loop, and — properly — give
`OMSOrder` a lock or move execution persistence off the coordinator's critical section entirely.

**Confidence** high — root cause read from the traceback, consequences read from the live tables.

### [CRITICAL] That job failed on attempt 1 of 3 and was never retried — and a retry would have double-submitted

**Location** `app/backend/app/services/worker_pool.py:315` (`_execute_job`); live `signal_jobs`

**Evidence**

```
job_id                               | status | attempt_count | last_error
e9d9148c-c6c2-4d8d-9eb7-69e3c50579a4 | FAILED | 1             | dictionary changed size during iteration
```

`max_attempts` is 3. The job went terminal at attempt 1.

**Problem** Two ways to lose. As it stands, a transient `RuntimeError` mid-basket kills the job
permanently with no operator signal. Had the retry fired, it would have re-run `coordinator.execute`
for a trade whose legs were already live at the broker — the idempotency key is computed per job,
not per emitted leg, so the second run would submit the close again and double the effect. The
`RECOVERY_REQUIRED` rows show the system knows this shape of problem exists
("`41 order(s) already emitted; requires reconciliation before retry`") but this error class does not
reach that guard.

**Fix** Route any failure that occurs after the first broker submission to `RECOVERY_REQUIRED`
unconditionally, never to `FAILED` and never to a blind retry.

**Confidence** high.

### [CRITICAL] Critical-basket auto-recovery never retries; the retry call is always a no-op

**Location** `app/backend/app/services/critical_recovery.py:99-106` (guard), `:107-128` (`_done`),
`:169-176`, `:232-239`, `:255-262`, `:286-293` (the five retry call sites)

**Evidence** `schedule_recovery` starts with:

```python
if key in self._in_flight:
    logger.debug("Critical recovery already in flight ...")
    return
```

`self._in_flight[key]` is only cleared by the `_done` callback, which runs when the task finishes.
All five retry call sites run *inside* that task. So every retry attempt hits the guard, logs at
`DEBUG`, and returns. The preceding `await asyncio.sleep(RECOVERY_RETRY_DELAY_SEC)` just holds the
task open for 30 seconds first.

**Problem** A CRITICAL basket whose first recovery attempt fails — TWS momentarily down, snapshot
timeout, broker still holding quantity — is never retried in-process. It stays CRITICAL, which
latches `mark_critical(account_id, strategy_id)` and blocks all new OPENs for that pair until a human
intervenes. The documented "retries once (~30s)" behaviour does not exist. Only a process restart,
via `enqueue_all_critical` at `main.py:135`, gives it another try.

**Fix** Register the retry outside the task — a delayed re-schedule owned by the service, not by the
attempt — or drop the in-flight key before sleeping.

**Confidence** high — traced the guard, the callback registration, and all five call sites.

### [CRITICAL] `_fanout_accounts` uses `asyncio.gather` without `return_exceptions`, so one account's failure cancels the others mid-submission

**Location** `app/backend/app/services/order_manager.py:508`

**Evidence** `outcomes = list(await asyncio.gather(*tasks))`. With the default
`return_exceptions=False`, the first exception propagates immediately and the sibling tasks are left
to be cancelled at an arbitrary await point.

**Problem** Those siblings are mid-`coordinator.execute`. A cancellation between "submitted to IBKR"
and "persisted to `orders`" produces exactly the missing-`CLOSE-L1` rows observed for accounts 294
and 297 above. This is the amplifier that turned a single-account persist bug into a multi-account
data-integrity incident.

**Fix** `return_exceptions=True`, then reduce per-account outcomes explicitly; treat any account that
raised as needing reconciliation rather than letting it disappear.

**Confidence** high on the mechanism; medium that it is the specific cause of the 294/297 gaps rather
than a second instance of the same iteration bug — both produce the same signature.

### [HIGH] Basket recovery runs before TWS is connected, so every incomplete basket is marked CRITICAL on startup

## The five things I would fix first

1. **Snapshot `order.executions` before iterating in `_persist_child`, and add
   `return_exceptions=True` to the fan-out gather.** Two small changes that stop the active
   data-integrity incident. Right now the system can submit orders to IBKR, fail to record them, and
   report the signal as rejected — and it did that twice today, leaving accounts 294 and 297 holding
   one leg of a pair. Nothing else matters until orders and the database agree.

2. **Reconcile accounts 294 and 297 by hand, today.** This is an operational action, not a code fix,
   and it comes second only because the code fix stops the bleeding. There is live residual exposure
   the system believes is closed, and `broker_positions` is too sparse (21 rows) to be trusted to
   surface it.

3. **Turn on webhook authentication and take the trading API off the public tunnel.**
   `WEBHOOK_AUTH_ENABLED=false` with a public ngrok URL pointed at port 8000 means anyone with the
   URL can inject orders into a system that is currently mis-recording the ones it already has. Then
   populate `EMERGENCY_KILLSWITCH_AUTH_SECRET`, because the documented break-glass control is
   presently rejecting every call.

4. **Fix the failure classification in the worker: any error after the first broker submission goes
   to `RECOVERY_REQUIRED`, never `FAILED` and never a blind retry.** Today's job went terminal on
   attempt 1 of 3 with orders live at the broker. The opposite outcome — a retry — would have doubled
   the close. Both directions are wrong and the code currently picks between them by accident.

5. **Fix the critical-recovery retry no-op and move `recover_incomplete_baskets` after TWS connect.**
   These compound: a restart with open baskets latches them all CRITICAL for want of a broker
   snapshot, and the auto-recovery that should clear them silently declines to retry. Together they
   can wedge trading for every affected account/strategy pair with no log above `DEBUG`.

Separately and not in the ranking, because it is cheap and unblocks everything else: **point the test
suite at a disposable database.** 91% of the durable queue and the only CRITICAL basket in the system
are test artefacts.

## [CRITICAL] `conftest.py` hands every test a live connection to the production database


database, no transactional rollback, no teardown, and no cleanup fixture. Every row a test creates

isolation in the suite protects a code path that does not execute, while the database has none.

**Problem** This is the origin of the entire chain: test accounts persist into production, they carry
`model_blue` allocations, the account router fans live signals out to them, the adapter sends their

holds 23× the intended position" runs through this fixture.
